# Décisions de design — phase 1

Tranchées à partir du 8 novembre 2026, après le premier jet du moteur. La spec, réécrite
le 10 novembre dans `docs/spec.md`, les intègre toutes ; ce fichier garde le pourquoi de
chaque choix. Une nouvelle décision s'ajoute ici et se reporte dans la spec.

Statut : **à appliquer** = décidé mais pas encore dans le code.

## Moteur

| # | Décision | Pourquoi | Statut |
|---|---|---|---|
| M1 | Modèle de flux par ticks pour tout le MVP, pas de simulation à événements discrets. | Suffit pour l'équilibrage et le rejeu en phase 2 ; un moteur à événements serait plus lourd à calibrer et à tester. | Fait |
| M2 | Pas de graine : le moteur n'a aucun aléa. Elle reviendra avec le premier élément aléatoire. | Un paramètre inutilisé n'a rien à faire dans la signature. | Fait |
| M3 | Pas de cascade de pannes par saturation : un aval saturé ne ralentit pas l'amont. La cascade par épuisement des fils est arrivée avec le circuit breaker, sa parade (S14). | Sans parade disponible, la cascade serait une punition, pas un choix. | Fait (S14) |
| M4 | Le SLA porte sur le taux d'échec global et sur la latence p95 des ticks, affichée « p95 (approx.) ». | Une moyenne cache les pics ; « p95 » colle au vocabulaire d'entretien, « approx. » évite de mentir sur ce qui est mesuré. | Remplacé par M15 |
| M6 | Les fils d'exécution d'un serveur se comptent **par envoi**, comme le travail : un lot de 100 messages sorti d'une file n'occupe qu'un fil. | Le worker du raccourcisseur, comptant 4 500 messages par seconde un par un, saturait ses fils au retour d'une panne alors qu'il ne recevait que 45 envois. Aucun rapport d'équilibrage ne bouge. | Fait |
| M5 | `requiresUpstream` devient une liste ; le scaling horizontal est permis derrière un load balancer **ou** une file. Depuis X8, ce sont deux évolutions : le serveur derrière un load balancer, le worker derrière une file ou un pub/sub. | Plusieurs workers consommant une même file est le pattern standard. | Fait |
| M7 | **Un tick vaut une minute** pour le joueur, une vague (60 ticks) montre une heure. Annoncé au premier briefing de chaque scénario (réplique du chambellan et ligne « En vrai », `theme.timeRule`) ; l'interface parle de minutes (« de la 31ᵉ à la 33ᵉ minute », « min 12 » sur l'axe des courbes), le code, le mode debug et les docs techniques gardent « tick ». Les débits restent en requêtes par seconde. **Aucun recalibrage** : seuls les textes changent (les durées s'écrivent en minutes à partir des ticks des incidents, `src/ui/time.ts`). Limite assumée : les compteurs cumulés (arriéré d'une file, capacité de 200 000 messages, requêtes en échec) additionnent des débits par seconde une fois par tick, donc **à l'échelle du jeu**, pas en volumes réels : la capacité d'une file se lit en minutes de trafic (arrivées par seconde × minutes d'attente), et la fiche de la file le dit. | À une seconde par tick, aucune durée opérationnelle n'était crédible : une instance d'autoscaling qui démarre en 2 secondes, un prestataire en panne 25 secondes. À une minute par tick, tout devient plausible sans toucher un chiffre (décision 5.2 de la revue, D3a). Multiplier les compteurs par 60 aurait forcé à tout recalibrer pour une exactitude que le jeu ne cherche pas (5.3 : des ordres de grandeur cohérents entre eux). | Fait |
| M8 | **La file impose le rythme de l'aval** (action M1 de la revue). Un message relâché par une file porte sa marque d'origine (`Stream.queue`) jusqu'à ce qu'il soit traité : ce qu'un nœud sur son chemin (worker, base, prestataire) ne peut pas servir par manque de capacité, fils ou quota compris, n'échoue pas, il **retourne dans sa file** à la fin du tick (`deferred` sur le nœud, `requeued` sur la file) et repart au tick suivant. Le trafic direct passe d'abord ; les messages de file prennent la capacité qu'il laisse (sur la base, le primaire, les lectures prenant d'abord les réplicas), ne comptent pas dans l'effondrement des clients qui relancent (S19) et ne sont jamais relancés par eux. Un message rendu compte dans l'arriéré maximal : une file que l'aval ne vide pas assez vite déborde (`queue-overflow`). Restent des échecs : la route manquante (`no-route`, un défaut de construction), et le message empoisonné mis de côté par la file des lettres mortes (`dead-lettered`, S25). Le disjoncteur ne peut pas couper un message de file : seul un worker consomme une file (#1), et il n'en a pas. Pas de délai de visibilité ; le compte d'essais ne vise que le message empoisonné (S25). Chaque pub/sub → file garde sa propre marque, un doublon rendu reste un doublon. | Le moteur faisait vider tout l'arriéré d'un coup par le worker revenu, et la base faisait échouer l'excédent : 260 clics perdus pour une panne de 2 ticks, 6 455 et la vague perdue pour 4 (revue, 3.2). Le jeu enseignait qu'une file perd les messages d'une panne longue, l'inverse de sa raison d'être. Un consommateur qui ne peut pas écrire n'acquitte pas. Une passe unique en ordre topologique ne sait pas d'avance ce que l'aval absorbera (la base sert aussi le trafic direct, traité ailleurs dans le graphe) : rendre l'excédent après coup couvre plusieurs sauts et la contention. Sans priorité, l'arriéré relâché ferait échouer les écritures des clients à parts égales. Limite assumée : la file relâche encore ce que son consommateur immédiat peut prendre, donc le lien file → worker → base montre l'arriéré entier qui circule ; seul `deferred` dit ce qui est revenu. Effet d'équilibrage : seule la vague 5 du raccourcisseur bouge (aucun échec de vidage) ; les autres files ne se vidaient pas sur une base saturée. | Fait |
| M9 | **Une panne touche aussi les instances d'autoscaling** (action M2 de la revue, B1). `instance-down` retire `count` instances d'un serveur : d'abord ses instances fixes, puis ses instances à la demande, **celles qui démarrent pendant la panne comprises** (elles démarrent avec la même version cassée). Une panne qui couvre tout le type (le déploiement raté du tournoi, `count: 10`) éteint donc tout, et une instance lancée pendant la panne ne sert qu'après elle. L'autoscaler garde son calcul (contre les instances fixes en service) : il demande des instances pendant la panne, qui servent dès qu'elle finit. `NodeTick.down` compte aussi les instances à la demande. | L'autoscaler gardait les siennes et en relançait une aussitôt : « 1 instance + autoscaling 3 » passait de 2 à 1 instance au lieu de 0, et la stratégie autoscaling de la tempête de relances gagnait parce qu'elle ne subissait pas l'incident annoncé. Ce que l'autoscaling fait bien reste : absorber, une fois la panne passée, le surplus des relances. Effet d'équilibrage (avec X10) : vague 1 du tournoi, « backoff + autoscaling » perd (latence p95 77 ms) et « scaling + autoscaling » ne gagne plus qu'au plafond de 6 instances (149,58) ; vague 4, l'autoscaling sans backoff perd (p95 208 ms). Le raccourcisseur ne bouge pas (sa panne de la vague 3 ne retire qu'une instance fixe sur deux). | Fait |
| M10 | **Relances par source, l'événement suit sa requête** (action M3 de la revue, B2, B3, B10, B12). Le grand livre du tick compte les échecs **que le client voit**, par source et par type (`Ledger.clientFailed`) : saturation, route manquante, rate limiting, circuit coupé. Chaque source ne relance que les siens, chaque type en lui-même (une lecture perdue revient en lecture). Une requête relancée **réémet son événement** s'il a échoué avec elle : au plus un par requête relancée, au prorata de la source (C5). Ne se relancent pas : un doublon traité deux fois, une copie non livrée, un événement perdu après la réponse, une lecture périmée, un message de file (M8). **L'effondrement capacité / charge (S19) ne frappe que la part du travail d'un nœud venue de sources qui relancent** : charge = demande + part × (demande² / capacité − demande). Un nœud que ces clients n'atteignent pas rejette vite son excédent, comme sans relance. | B2 : 150 billets jamais envoyés en vague 1 du tournoi alors que les achats relancés avaient réussi. B3 : les échecs étaient répartis entre les sources qui relancent au prorata de leur débit, quelle que soit la source en échec (faux dès qu'un scénario mêlera partenaires sans relance et clients avec). B10 : un doublon, enregistré sans part async, était relancé comme une lecture. B12 : l'effondrement s'appliquait à tout nœud saturé dès qu'une seule source relançait. La règle par part reste simple (une interpolation entre les deux régimes) et juste : seul un client qui abandonne laisse du travail perdu derrière lui. Effet d'équilibrage : aucune stratégie ne bouge ; les réponses du tournoi qui relancent passent de 84–89 % à 100 % de marge d'échec (les billets relancés arrivent). | Fait |
| M11 | **Délestage**, évolution du load balancer (10, +1) : au-delà de 75 % de ce que les serveurs derrière la porte peuvent servir ce tick (instances tombées déduites, instances à la demande prêtes comprises), la porte refuse tout de suite l'excédent, en échec `load-shed`. Les serveurs ne s'effondrent plus sous des requêtes déjà abandonnées (S19) ; les refus restent des échecs que les clients relancent. | Le backoff demande d'écrire le client ; l'opérateur, lui, possède sa porte. Laisser entrer 100 % de la capacité tenait les serveurs à pleine charge, où la latence décroche (p95 à 203 ms en vague 1 du tournoi) : un délesteur réel coupe avant, sur la latence ou l'attente, d'où la charge cible. Effet d'équilibrage : troisième réponse de la vague 1 du tournoi (délestage + 1 instance, 150) ; en finale, il ne gagne qu'avec le backoff, les trois incidents ensemble demandant aussi des clients qui espacent leurs relances. Budget de la vague 2 du tournoi 150 → 155, pour que la réponse « délestage » ne mène pas dans le mur ; l'autoscaling y redevient une seconde stratégie, plus chère (150,42). | Fait |
| M12 | **Une dépendance qui ne répond plus retient les fils jusqu'au délai du client** (5 000 ms), comme une lenteur ; un composant dont les instances refusent répond, lui, dans sa latence de base. **Délai d'attente**, évolution du serveur (5, +1) : un appel direct qui dépasse 300 ms (1 000 ms depuis S24) est abandonné, en échec `timed-out` ; il garde un fil au plus ce temps-là, et le client attend tout le délai. Un disjoncteur ouvert passe avant : il coupe sans attendre. La latence affichée d'un nœud sans instance n'est plus l'artefact de 20 × sa base (B5). | Une panne totale coûtait moins cher qu'une lenteur : chaque appel échouait gratuitement, sans retenir un fil, et le disjoncteur n'y changeait rien (revue 3.6). C'est l'inverse en vrai : un prestataire qui se tait est le cas le plus destructeur. Gradation obtenue au banquier, vague 2 : sans rien, cascade (p95 4 219 ms) ; délai seul, la cascade s'arrête mais la commande attend 300 ms ; disjoncteur, la vague tient ; vague 4, prestataire fermé sans file : 18,8 % d'échecs au lieu de 1,4 %. Le délai seul n'est la réponse d'aucune vague, et c'est voulu : c'est la première protection, pas la dernière. Aucune stratégie gagnante ne change. | Fait |
| M13 | **Âge du plus vieux message** de chaque file, par tick (`NodeTick.backlogAge`, en minutes pour le joueur) : affiché sur le plateau et dans les courbes ; le debrief alerte au-delà de 10 minutes, même sans perte. **Pas d'objectif de fraîcheur** dans le SLA. | C'est ce qu'on surveille sur une vraie file, plus que sa longueur. L'objectif de fraîcheur prévu (revue, D2) a été écarté : au banquier, la file se vide d'un coup au retour du prestataire, l'objectif ne se perdrait jamais ; au tournoi, le quota du prestataire empêche le rattrapage (environ 30 minutes de retard jusqu'à la fin) et aucune parade du jeu ne l'accélère. Sans parade, l'objectif serait une punition (même raison que M3). | Fait |
| M14 | **Un événement que k services attendus sur n n'ont pas reçu compte pour k / n d'échec** (B9 de la revue). « Non livré » et les autres échecs d'une copie restent comptés en messages, copie par copie, dans `failuresByReason`, les nœuds et les courbes ; le taux d'échec du SLA, lui, pèse chaque copie d'événement perdue 1 / n (`WaveResult.failed`, `TickMetrics.clientFailedSoFar`). Le dénominateur ne change pas (des requêtes). Les courbes lisent ce même cumul (relances déduites, ce qu'elles ne faisaient pas). | Le taux divisait des copies par des requêtes : le marché sans livraison affichait 119 % d'échecs à la vague 2 (69 % désormais). Une commande à moitié livrée est à moitié en échec ; jamais livrée, elle compte pour un, pas pour trois. Au passage, un événement relancé avec sa requête ne laisse plus derrière lui n − 1 copies en échec (aucun scénario à relances n'a plus d'un service attendu). Effet d'équilibrage : aux soldes du marché, l'événement perdu avant publication ne comptait plus que pour un au lieu de trois, et « scaling 2 + idempotence + cache », sans outbox, gagnait (0,53 % d'échecs) ; l'incident passe de 15 minutes à 40 % (35 → 50) à 20 minutes à 80 % (30 → 50). Rien d'autre ne bouge, l'instantané est identique. | Fait |
| M15 | **La latence se mesure par chemin, pondérée par le débit** (action M4 de la revue, 3.1, 3.10, 3.11). À chaque tick, chaque classe de requête (source × type) donne un point par chemin servi : sa latence de bout en bout et le débit des réponses passées par lui. Une lecture servie par le cache et une lecture qui l'a raté et attend la base sont deux points ; une bordure qui sert sa part en est un, ce qu'elle laisse passer un autre ; derrière une file, le chemin s'arrête à la file ; un pub/sub copie l'événement à chacun, le client attend la copie la plus lente. **La latence de la vague est le 95ᵉ centile pondéré de tous ces points** : la plus petite latence telle que les réponses aussi rapides pèsent au moins 95 % des réponses de la vague. Une minorité lente se voit dès qu'elle pèse plus de 5 %, sans règle à part. **Les échecs n'y sont pas** : un refus (saturation, rate limiting, délestage, disjoncteur, route manquante, instance arrêtée) est immédiat et n'est que dans le taux d'échec ; mais un appel abandonné par le délai d'attente compte pour l'attente (sa latence d'amont plus le délai), et un appel à une dépendance qui se tait pour le délai du client (M12) : ces clients-là ont attendu. **Objectif propre à un type** (`sla.maxP95LatencyMsByKind`, en données, optionnel) : ses réponses sont jugées à part, sur leur propre p95, et sortent de l'objectif général ; la jauge retient l'objectif le plus serré, une raison de défaite par objectif dépassé (« latence p95 des événements »). Le marché, le banquier et le tournoi jugent ainsi l'événement de la commande (60 ms) : c'est ce que faisait S17. `TickMetrics.slaLatencyMs` est le p95 des réponses du tick (même règle sur un seul tick, objectif général), avec `answeredRps` et `slowRps` ; `latencyByKind` donne la même chose pour chaque objectif propre. **Tick de rupture** (`latencyBreachTick`) : pour chaque objectif perdu, le premier tick où les réponses plus lentes que sa limite, cumulées depuis le début, pèsent plus de 5 % de ses réponses sur toute la vague ; le plus tôt des objectifs perdus. C'est exact : la vague est perdue si et seulement si ce poids final dépasse 5 %. Affichage « p95 », sans « (approx.) » : c'est un vrai centile par requête, à la granularité de la minute (toutes les requêtes d'un même chemin dans une même minute ont la même latence). | Le p95 des ticks par rang le plus proche écartait les 3 pires minutes sur 60, exactement la taille des incidents courts (revue, 3.1) ; la moyenne par tick noyait une minorité lente, d'où deux rustines, S17 (l'événement direct) et S21 (les lectures à jour au-delà de 5 %, avec un effet de falaise) ; et une requête en échec gardait une latence moyenne (3.10). Une seule règle les remplace. Les refus hors de la latence : c'est la convention la plus courante (latence des succès), et les échecs ont leur jauge. L'attente d'un délai d'attente y reste : sans elle, le délai seul vaudrait le disjoncteur, et la gradation de M12 disparaissait. L'objectif propre à la commande vient de S17 : 80 commandes sur 1 660 requêtes aux soldes, 30 sur 330 au banquier, 50 sur 1 700 au tournoi ne pèsent pas 5 % ; le briefing promet pourtant au client sa commande en 60 ms. Une rustine de moins : c'est une donnée de la vague, que la fiche peut dire. Effet d'équilibrage, dès qu'un cache sert 95 % des lectures : ses absences et les écritures pèsent plus de 5 %, le p95 est le chemin serveur + base. Raccourcisseur, vague 3 : CDN + réplica perd (base à 87 %, 72 ms), l'autoscaling demande 2 instances fixes (153,33 ; sur une seule, la montée en charge sature) ; vague 4 : sans CDN, 4 instances de plus (180) et le seul palier 40 (à 80, le scraper charge la base) ; la réponse CDN ne bouge pas (160). Marché, vague 5 : l'outbox double les écritures, la base à 93 % se voit ; réponse + réplica (305), budget 270 → 310, plafond 21 → 22, seuil 305 ; les impasses depuis les réponses à réplica de la vague 4 disparaissent. Banquier et tournoi : aucune stratégie ne bouge (objectif propre aux paiements et aux billets). | Fait |

## Économie et progression

| # | Décision | Pourquoi | Statut |
|---|---|---|---|
| E1 | Le coût est une facture par vague sous un plafond, sans réserve qui s'accumule. Retirer « or gagné entre les vagues » de la table des métaphores de la spec. | Colle au cloud réel : on paie ce qui tourne. Une épargne n'apprend rien en system design. | Fait |
| E2 | Retirer ou remplacer un composant coûte une fois sa valeur d'achat. Réduire les instances est gratuit ; retirer un réplica ou désactiver le rate limiting coûte. Réglé par évolution dans les données (`removalCost`). | Sans friction, défaire ne coûte rien et le réflexe « anticiper le coût d'une décision passée » disparaît. | Abandonnée (E8) |
| E3 | Le coût de migration entre dans la facture de la vague, contre le même plafond ; le debrief l'affiche sur une ligne « migration ». | C'est la leçon : un choix de la vague 2 peut coûter la vague 3. | Abandonnée (E8) |
| E4 | Une vague perdue se rejoue sans limite, depuis l'architecture de fin de la vague précédente. Pas de défaite définitive en phase 1. | Refaire les vagues déjà gagnées n'apprend rien. | Fait (`engine/game.ts`) |
| E6 | On peut revenir au début de toute vague déjà atteinte, avec l'architecture validée à ce moment-là ; le retour compte comme un rejeu de la vague visée et efface les scores suivants. | Sans ça, un choix passé peut bloquer la partie : depuis le parcours CDN (vagues 3 et 4), aucune architecture ne gagne la vague 5, et le rejeu repartait toujours de la vague 4. | Fait |
| E7 | **Trois étoiles par vague**, une par objectif : tenir la vague, la tenir du premier coup, et rester économe (facture ≤ `thriftyCost`, calé sur la stratégie gagnante la moins chère). Le score reste à côté. | Des objectifs lisibles avant de jouer, là où le score est une moyenne de marges opaque. L'étoile d'économie récompense la réponse la plus fine sans punir les autres stratégies, qui gagnent quand même. | Fait |
| E5 | Score d'une vague = 100 × moyenne des marges (coût, complexité, échecs, latence), bornée à [0, 1], moins 20 % par rejeu, sans descendre sous zéro. Score de partie = somme des vagues. Coefficients en données. L'écran ne montre jamais une pénalité au-delà de 100 % : passé cinq rejeux, il dit « la vague ne rapporte plus de points ». | Récompense la marge, comme le dit la spec, et pénalise les essais à l'aveugle. Le « −260 % » affiché après 13 rejeux ne voulait rien dire. | Fait |
| E8 | **Démolir est gratuit** (abandonne E2, E3 et B7). La facture d'une vague ne compte que ce qui est bâti : `simulateWave(arch, wave, catalog)` ne reçoit plus l'architecture précédente, `removalCost` disparaît du catalogue, le contrôle d'enchaînement de `npm run balance` aussi, et l'aide ne propose plus de revenir en arrière ni ne signale un bâtiment « démoli puis reposé ». Les budgets relevés pour absorber une migration (finale du tournoi : 250) restent tels quels. | Le jeu est didactique : payer pour corriger son architecture punit d'apprendre de ses erreurs. Le coût n'était montré qu'en « budget dépassé, dont N de migration », jamais au debrief (E3 n'a pas été fini), et il a fallu trois mécanismes pour le compenser (E6, B7, deux indices). La leçon « un choix passé engage » est réelle, mais c'est un sujet à part : le mode migration des suites. | Fait |

## Compromis

| # | Décision | Pourquoi | Statut |
|---|---|---|---|
| C1 | Le rate limiting se règle par paliers définis en données (10, 20, 40, 80, 160 req/s par client) ; le niveau de l'évolution est l'index du palier. | Rend réel le compromis « peut rejeter du trafic légitime », et donne des valeurs discrètes à l'énumération et aux menus. | Fait |
| C2 | Une source « partenaires » légitime à fort débit (ordre de grandeur : 50 clients à 30 req/s) dès la vague 4, scraper recalibré pour qu'une fenêtre de limite gagnante existe sans être évidente. | Avec des clients légitimes tous identiques, toute limite au-dessus de leur débit est gratuite. | Fait : 50 partenaires à 30 req/s, scraper sur 2 adresses à 1 000 req/s en longue traîne (calibrage actuel, voir le tableau du raccourcisseur) |
| C3 | Péremption du cache et retard de réplication hors MVP. | Le raccourcisseur a des données immuables : aucune vague ne peut les punir. | Reporté |
| C5 | Le rate limiting ne compte que le trafic synchrone ; l'async (un clic par redirection) suit le sort de sa requête sans entamer le quota. | Un événement de clic est un effet de bord côté serveur, pas une requête du client. Sans ça, la vague 5 coupait les partenaires. | Fait |
| C6 | **L'async d'une requête rejetée par le rate limiting est compté** (B8) : pour un client légitime, c'est un échec `rate-limited`, compté comme événement en échec (il ne sera ni livré ni relancé) ; pour un client abusif, il est écarté avec lui (`shed`), hors échecs. Le quota reste calculé sur le seul synchrone (C5). | C5 voulait que l'async « suive le sort de sa requête », mais le limiteur le réduisait sans le compter nulle part : ni servi, ni échoué (écart E1 de l'invariant de conservation), alors que le CDN compte en échec (`lost-at-edge`) l'async qu'il perd. Aucun rapport d'équilibrage ne bouge : aucune réponse attendue ne rejette de client légitime. | Fait |
| C7 | **La passerelle d'API** (ticket n° 2) **complète la limite unique du load balancer, elle ne la remplace pas.** Composant `api-gateway` (25, +2 de complexité, 5 ms), posé à l'entrée : derrière le CDN, devant le load balancer. Il **réutilise le comportement `balancer`** : aucun comportement nouveau, une seule donnée de plus au moteur. Une source déclare sa **classe** (`TrafficSource.class` : `partner` pour une clé d'API, `anonymous` sinon, scraper compris), et l'effet `rateLimit` prend une `class` optionnelle : une limite de classe ne voit que les sources de sa classe ; sans classe, elle voit tout le monde (la limite unique, C1). Deux évolutions de la passerelle, aux mêmes paliers que C1 (10 à 160 req/s par client, 5 chacune, +1) : **quota par clé d'API (partenaires)** et **limite par adresse (anonymes)**. Le quota reste sur le seul synchrone (C5), l'async suit sa requête (C6), l'abusif écarté reste hors échecs (`shed`). La passerelle ne répartit pas : le scaling exige toujours un load balancer, et une passerelle posée entre lui et le serveur ne s'y insère pas (I11). **Vague 5 du raccourcisseur, « À chacun sa limite »** (le comptage des clics devient la vague 6) : 12 partenaires à 125 req/s par clé, une clé de partenaire dont le script boucle (2 000 req/s, abusive), un scraper réparti sur 20 adresses à 60 req/s, des visiteurs à 3 req/s. À 80 et en dessous, la limite unique coupe les partenaires ; à 160, le scraper passe et noie la base ; l'absorber (3 réplicas, 6 instances, 320) dépasse le budget. Réponses : 160 par clé et 10 par adresse, avec CDN et 2 instances de plus (210), ou sans CDN avec 4 instances de plus et un réplica (250) : le saut de 5 ms coûte une instance. | S25 | **File des lettres mortes** (ticket n° 3), une **évolution de la file** (5, +1), pas un bâtiment : après `maxReceives` essais ratés (3, en données), un message empoisonné est mis de côté ; il ne revient plus et compte en échec `dead-lettered` (pas un échec que le client voit, jamais relancé : sa commande a été confirmée ; il pèse dans le taux d'échec comme une copie non livrée, 1 / n, M14). **Incident `poison-message`** (en données, annoncé au briefing, X5) sur un type de file : une part `share` des événements déposés pendant l'incident est empoisonnée (`Stream.poisoned`, le nombre d'essais ratés). Une part coûtant son seul travail ne pesait rien (le service sert 100 000 messages par seconde en lots de 100), et une file qui ne perd rien ne fait perdre une vague que par la latence ou la perte ; la file bloquée, elle, perd vraiment ce qui attend derrière tant que rien ne retire le message : c'est le cas d'école (un consommateur qui plante en boucle sur le message en tête, une file FIFO ou une partition Kafka). Les lettres mortes en échec : le travail n'est pas fait, et le debrief dit qu'il faut les examiner puis les rejouer (redrive) ; à 5 % de cinq minutes, elles pèsent 0,10 % d'échecs à la vague 5, 0,02 % aux soldes. ## Quatrième scénario : le grand tournoi

| # | Décision | Pourquoi | Statut |
|---|---|---|---|
| S18 | Quatrième scénario, **le thème Distribué** : la billetterie d'un tournoi, prise d'assaut. Même cité ; le prestataire d'e-mail (`mail-provider`, le colombier, hors palette) est déjà sur le plateau. Quatre vagues : tempête de relances, file qui déborde, partition, puis les trois ensemble. | Rassemble ce qui restait des suites (partition réseau, tempête de réessais, une file qui déborde) dans un récit où chaque incident a une conséquence évidente : une place vendue deux fois, un billet jamais reçu. Quatre vagues suffisent à trois mécanismes. | Fait |
| S19 | **Relances des clients** : une source déclare `retries`. Chaque échec synchrone revient au tick suivant, tous ensemble, jusqu'à `retries` relances par requête neuve. Un échec relancé n'est pas vu du client : il sort du taux d'échec, sa relance compte à sa place (le rejeu fait de même). Quand des clients relancent, un nœud saturé (serveur, base) ne rejette plus vite : il traite des requêtes déjà abandonnées et ne sert que capacité / charge de ce qu'il pourrait. Parade : **backoff exponentiel et jitter**, évolution des clients (5, +1), qui étale les relances sur 10 ticks (10 minutes depuis M7) ; ou l'autoscaling, qui absorbe la tempête. Une lecture périmée n'est pas relancée : le client ne sait pas qu'elle est fausse. Depuis M10, chaque source relance ses propres échecs, avec leurs événements, et l'effondrement ne frappe que la part du trafic qui relance. | Sans cet effondrement, une panne brève se résorbe seule et la tempête n'existe pas : c'est le travail perdu pour des clients partis qui la rend métastable. Compter chaque tentative comme un échec rendait le backoff inutile, alors que sa vertu est justement de faire réussir la relance. | Fait |
| S20 | **File bornée et quota** : la file garde 200 000 messages ; au-delà, elle déborde (échec `queue-overflow`). La **rétention** (5 par niveau, +1 de complexité) ajoute 100 000 messages par niveau. Un prestataire externe a un quota (`maxRps`) compté en messages, lots compris : une file qui le consomme ne se vide pas plus vite. | La leçon : une file absorbe un pic ou une panne de l'aval, pas un excès qui dure, et se dimensionne sur la plus longue panne qu'on accepte (arrivées × durée). Une limite de quelques milliers cassait le raccourcisseur, dont la file reçoit 4 500 clics par seconde : 200 000, c'est 45 secondes de clics (4 500 par seconde). Depuis M7, un tick additionne ce débit et vaut une minute : le jeu les lit comme 45 minutes de trafic, à l'échelle du jeu. | Fait |
| S21 | **Partition réseau** (incident `partition` sur la base) : les réplicas sont coupés du primaire. Une source `consistent` (les places restantes) lit des données qui doivent être à jour : jamais en cache, et la part de ses lectures servie par des réplicas coupés est un échec `stale-read`. **Lecture sur le primaire**, évolution de la base (5, +1) : ces lectures vont au primaire d'abord. Leur latence compte à part dans le SLA dès qu'elles pèsent plus de 5 % du trafic (règle générale depuis M15). | Le choix CAP rendu jouable : pendant une partition, disponible ou cohérent, donnée par donnée. Sans la mesure à part, une base saturée par ces lectures restait invisible derrière 2 000 lectures servies par le cache, et une finale sans réplica gagnait (trouvé par `npm run balance`). | Fait |
| S22 | **« Rétention » devient « Capacité de la file »** côté joueur ; l'id `queue-retention` reste, pour les sauvegardes. | En vrai, la rétention d'une file est une durée (Amazon SQS : 4 jours par défaut, 14 au plus), pas un nombre de messages : le mot enseignait un contresens. La leçon du débordement le dit, avec Kafka (durée ou octets) et RabbitMQ (longueur). | Fait |
| S23 | **La vague 3 du tournoi parle de la vérification avant achat**, plus des « places restantes ». Même mécanique (source `consistent`, S21). | Afficher un nombre de places un peu périmé est bénin ; confirmer une place déjà vendue ne l'est pas. Le briefing et la leçon disent que la garantie finale contre la double vente est une réservation atomique à l'écriture. | Fait |
